# `SUPPLY-001` — Supply Chain Policy and SBOM

Roadmap item: `SUPPLY-001`
Recorded: 2026-08-04
Status: dependency, licence, lock, and SBOM policy enforced by tests; artifact
signing recorded as a position; gate `G2` still open

`SUPPLY-001` asks for advisory, dependency, and licence checks, a lock and
reproducibility policy, artifact provenance, a checksum and signing policy, and
an SBOM. Where a policy can be enforced by a test it is, because a policy that
lives only in a document is a policy that drifts.

## 1. The SBOM is generated, and drift is a test failure

`sbom/paddleocr-rust.cdx.json` is CycloneDX `1.5`, generated by
`tools/generate_sbom.py` from `Cargo.lock`. It lists all `48` locked packages
with name, version, `purl`, licence expression, distribution source, and the
SHA-256 of the published `.crate` archive.

A hand-written SBOM goes stale on the first dependency change, and **a stale SBOM
is worse than none**: it asserts a composition that is no longer true. So
`tests/supply_chain.rs` requires exact correspondence in both directions —
every locked package appears in the SBOM, every SBOM component is still locked,
and versions and checksums match.

That check was verified to actually fail: removing one component from the SBOM
produces

```
locked but absent from the SBOM: ["png"] — regenerate with
tools/generate_sbom.py and review the additions
```

A test that has never been seen to fail is not yet evidence of anything.

The document carries **no timestamp**. It is the one field that would change on
every regeneration, which would make the committed file impossible to diff and
impossible to check for drift.

## 2. Licences are checked against a reviewed list

`every_licence_in_the_graph_has_been_reviewed` compares each component's
expression against an explicit list of nine reviewed expressions. It is a list
rather than a permissive-by-pattern rule on purpose: a new expression should fail
and be looked at **even when it is obviously fine**, because "obviously fine" is
exactly the judgement the review exists to make.

Current distribution across the `48` components:

| Expression | Count |
|---|---|
| `MIT OR Apache-2.0` | 31 |
| `MIT` | 5 |
| `Apache-2.0 OR MIT` | 4 |
| `MIT/Apache-2.0` | 3 |
| `0BSD OR MIT OR Apache-2.0` | 1 |
| `ISC` | 1 |
| `Unlicense OR MIT` | 1 |
| `MIT OR Zlib OR Apache-2.0` | 1 |
| `(MIT OR Apache-2.0) AND Unicode-3.0` | 1 |

All permissive; no copyleft. Licences are read from the vendored crate sources
rather than a curated table, and a crate that cannot be read emits `NOASSERTION`
rather than a guess. None currently does.

Note that this covers the whole lockfile, including dev-only and build-only
packages that never reach a shipped binary. That is deliberate: a build-time
dependency still runs on a developer's machine.

## 3. Lock and reproducibility policy

- `Cargo.lock` is committed.
- Every direct dependency uses an **exact** `=` requirement, enforced by
  `every_direct_dependency_is_exactly_pinned`. A caret requirement would let a
  rebuild pick up a version nobody in this repository has looked at.
- Every build and test command in this project uses `--offline --locked`, so a
  build cannot silently resolve something new.
- The toolchain is pinned; `rustc 1.94.0` is recorded in every measurement.

The result is that the audited graph is the built graph. That property is what
makes the rest of this document meaningful.

## 4. Checksums and provenance

Three layers, each verifiable without trusting this project:

| Layer | Mechanism |
|---|---|
| Rust dependencies | SHA-256 of each published `.crate`, from `Cargo.lock`, carried into the SBOM |
| Model artifacts | SHA-256 declared in the `MOD-002` manifest and verified by streaming before the model is loaded |
| Runtime library | SHA-256 recorded in `G3_RESOURCE_EVIDENCE.md`; **not** verified by this project, because the caller passes a path and the library is loaded by the OS |

The third row is a real gap and is stated as one. This project checks the models
it loads and does not check the runtime library it loads them into.

## 5. Signing

**Position: this project signs nothing, and verifies no signature.**

It produces one binary and no distributed artifacts. Signing is meaningful at a
distribution boundary, and this project has not crossed one: there is no release,
no package, and no download endpoint. Adopting a signing scheme now would mean
choosing a key custody model for a distribution that does not exist.

When a release is prepared — `P14` — a signing policy is a prerequisite, not an
afterthought, and it will need to cover the binary, the SBOM, and the manifest
together, since a signed binary with an unsigned manifest leaves the artifact
identity unprotected.

## 6. Advisories

There is no vendored advisory database and no network, so no advisory scan runs
here. What reduces the exposure is the shape of the graph rather than a scanner:
`48` packages, one direct dependency by default, one build script in the entire
tree, and every version exactly pinned so a scan result stays valid until
someone deliberately changes it.

A `cargo audit` or `cargo deny` step belongs in whatever CI a release is built
by, and `tests/supply_chain.rs` is the part that can run without a network.

## 7. Open

- **Gate `G2`** — the ONNX Runtime binary has no hermetic rebuild and no SBOM of
  its own, and cannot fully close on this host because the source-tag
  signature's public key is not available locally. Everything above concerns
  this project's own supply chain; `G2` concerns the one dependency this
  document cannot generate an SBOM for, because it is not a Cargo package.
- **No advisory scan**, per §6.
- **No signing**, per §5, deliberately and until there is something to sign.
